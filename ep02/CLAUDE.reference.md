# 프로젝트 지침: AI 24/7 자동매매 트레이딩 시스템

> 이 문서는 프로젝트의 **헌법**이다. Claude Code / 협업 AI / 개발자 모두 이 지침을 따른다.
> Claude Code 사용 시 이 파일을 레포 루트의 `CLAUDE.md`로 복사(또는 심볼릭 링크)한다.

## 1. 프로젝트 목적

업비트 KRW 현물 시장에서 **논문 기반 전략 + ML 예측 + LLM 거시 판단**을 결합해 24/7 자동으로 매매하고, 모든 매매의 근거를 텔레그램과 대시보드로 투명하게 보여주는 시스템을 만든다.

**우선순위 (충돌 시 위가 이긴다):**
1. 자본 보전 (리스크 한도 준수)
2. 시스템 안정성 (무중단, 장애 시 안전 정지)
3. 설명 가능성 (모든 결정에 근거 기록)
4. 수익성
5. 개발 속도

## 2. 핵심 원칙 (반드시 지킬 것)

1. **검증 없는 실전 없음.** 어떤 전략/모델도 `백테스트 통과 → 페이퍼 트레이딩 2주 이상 → 소액 실전` 순서를 건너뛸 수 없다.
2. **LLM은 제안자, 리스크 엔진은 결정자.** LLM 출력은 `RiskManager.validate()`를 통과해야만 주문이 된다. 리스크 엔진을 우회하는 코드 경로를 만들지 않는다.
3. **백테스트 ≡ 실전 로직.** `Strategy`, `RiskManager` 클래스는 백테스트와 실전이 동일한 코드를 import한다. 백테스트 전용 분기(`if backtest:`)로 로직이 달라지면 안 된다.
4. **룩어헤드 금지.** 의사결정은 봉 마감 후, 체결은 다음 봉부터. 미래 데이터가 피처에 섞이는지 항상 의심한다.
5. **모든 결정은 기록된다.** 주문 여부와 관계없이 `decisions` 테이블에 입력 컨텍스트, 모델 출력, 리스크 판정, 최종 액션을 남긴다.
6. **작게, 점진적으로.** 유니버스는 메이저 코인부터, 자본은 소액부터, 기능은 Phase 단위로.
7. **추상화 우선.** 거래소(`ExchangeBase`)와 LLM(`LLMBase`)은 인터페이스로 분리. 구현체 교체만으로 바이낸스/다른 모델 추가가 가능해야 한다.
8. **시크릿은 코드에 없다.** API 키·토큰은 `.env`에만. 로그와 텔레그램 메시지에도 절대 노출하지 않는다.
9. **느린 판단, 빠른 감시.** 전략·LLM 판단은 봉 마감/수 시간 주기. 손절·익절·킬스위치는 1분 주기 **Position Guard**가 LLM·전략과 독립적으로 실행한다. LLM API 장애가 포지션 보호를 멈추게 해서는 안 된다.
10. **에이전트는 무상태, 기억은 파일에.** LLM 호출은 매번 `memory/`의 Markdown을 읽고 끝나면 갱신한다. 숫자(잔고, 손익, 체결)의 진실은 DB, 맥락(시황 테제, 교훈)의 진실은 메모리 파일. 둘이 충돌하면 DB가 이긴다.
11. **개발 도구와 실전 경로를 섞지 않는다.** Claude Code 루틴, 트레이딩뷰 MCP, `/loop` 분석은 리서치·리포트용이다. 실전 주문은 서버에서 도는 Python 프로세스만 낸다.

## 5. 개발 규칙

### 5.1 코드
- 모든 함수에 타입힌트. 공개 함수에 docstring(한 줄이라도).
- 금액·수량은 `Decimal` 사용 (float 오차로 최소주문금액 미달 사고 방지).
- 시간은 항상 **UTC-aware `datetime`**. 표시할 때만 KST 변환.
- 외부 API 호출은 타임아웃·재시도(지수 백오프)·레이트리밋 준수를 래퍼에서 처리.
- 매직 넘버 금지. 전략 파라미터·리스크 한도는 `config/`의 YAML/설정 객체에서 온다.
- 하나의 PR/커밋은 하나의 관심사. 리팩토링과 기능 변경을 섞지 않는다.

### 5.2 테스트
- `risk/`, `execution/`, `backtest/`는 **단위 테스트 커버리지 90% 이상**.
- 주문 로직 변경 시 페이퍼 거래소 구현체로 통합 테스트 필수.
- `tests/backtest_regression/`: 기준 전략의 백테스트 지표가 허용 오차를 벗어나면 CI 실패 → 의도치 않은 로직 변경 감지.
- LLM 호출은 테스트에서 모킹. 실제 호출은 `@pytest.mark.live`로 분리.

### 5.3 브랜치·커밋
- `main`은 항상 배포 가능 상태. 기능은 `feat/*`, 수정은 `fix/*`.
- 커밋 메시지: `type(scope): 요약` (예: `feat(risk): 일손실 한도 추가`).
- 실전 운영 중인 코드 변경은 **페이퍼 모드에서 최소 24시간 검증 후** 배포.

### 5.4 Claude Code 작업 방식
- 작업 시작 전 `ROADMAP.md`에서 현재 Phase와 완료 기준을 확인하고, 범위를 벗어나는 기능은 제안만 하고 구현하지 않는다.
- 새 모듈은 항상 테스트와 함께 만든다.
- 설계상 중요한 선택(라이브러리 교체, 스키마 변경)은 `docs/decisions/`에 ADR로 남긴다.
- 불확실한 거래소 스펙(수수료, 레이트리밋, 최소주문금액)은 추측하지 말고 코드에 `# TODO: verify` 표시 후 사용자에게 확인 요청.

### 5.5 글쓰기 규칙 (문서, 주석, 커밋 메시지, 텔레그램 메시지, 메모리 파일, LLM 프롬프트 출력 전부 해당)
- **em dash(U+2014)와 en dash(U+2013)는 쓰지 않는다.** 문장을 나누려면 마침표나 쉼표, 괄호를 쓴다. pre-commit 훅(`scripts/check_dashes.py`)이 이 두 문자를 찾으면 커밋을 막는다. 이 지침 파일 자체도 검사 대상이라 문자 대신 코드포인트로 적는다.
- **AI 말투와 번역투를 피한다.** 한국어로 쓰되 사람이 직접 쓴 글처럼 쓴다. 구체적으로:
  - "~하는 것이 중요합니다", "~할 수 있습니다", "~를 보장합니다", "~에 도움이 됩니다" 같은 습관적 마무리를 쓰지 않는다. 짧게 끊어서 단정한다.
  - "genuinely", "robust", "seamless", "leverage" 같은 영어 단어를 그대로 옮긴 말투(진정으로, 견고한, 매끄러운, 활용하여)를 남발하지 않는다.
  - 사물 주어 수동태("~에 의해 수행됩니다")보다 능동태("~가 한다")를 쓴다.
  - 도입부 인사, 요약 반복, 과장된 강조("매우", "완벽하게")를 넣지 않는다. 본론부터 쓴다.
  - 텔레그램 메시지와 LLM `reason` 출력도 같은 기준이다. "시장 상황을 종합적으로 고려했을 때" 같은 빈 말 대신 근거가 되는 숫자와 사실만 적는다.
- 기술 용어는 통용되는 것을 그대로 쓴다(백테스트, 슬리피지, 레짐). 억지로 번역하지 않는다.
- 이 규칙은 Claude Code가 만드는 모든 텍스트에 적용된다. 프롬프트 파일(`src/app/llm/prompts/`)에도 이 규칙을 시스템 지시로 넣는다.

### 5.6 이 지침의 갱신 규칙
- 지침은 꼭 필요할 때만 고친다. 기준: 새 규칙이 없으면 구현 방향이 갈리거나, 기존 규칙이 실제 코드와 모순될 때.
- 취향, 표현 다듬기, 단순 보강은 지침에 넣지 않고 `docs/`나 ADR로 보낸다.
- 고칠 때는 버전을 올리고 상단에 변경 요지를 한 줄로 남긴 뒤, 운영자에게 갱신된 지침 전체를 알린다.

## 6. 데이터 규칙

- 원천 데이터(raw)는 수정하지 않고 별도 테이블/파일로 보존. 가공은 항상 재현 가능한 스크립트로.
- 캔들 타임스탬프는 **봉 시작 시각 UTC**. 마감 여부 컬럼(`is_closed`)을 두고 미마감 봉은 피처 계산에서 제외.
- 결측·중복·이상치 검사 스크립트를 수집 파이프라인에 포함. 실패 시 텔레그램 경고.
- 뉴스/거시 데이터는 **수집 시각(`fetched_at`)** 과 **발표 시각(`published_at`)** 을 모두 저장 (백테스트 시 "그 시점에 알 수 있었는가" 판단용).
- 경제 캘린더 이벤트에는 중요도(high/medium/low)와 방어 모드 적용 윈도우(기본 ±2시간)를 둔다.
- 데이터 소스별 라이선스·이용약관을 `docs/data_sources.md`에 기록.

## 7. 백테스트 규칙

1. **이벤트 드리븐**: 봉 마감 → 신호 → 다음 봉 시가(또는 보수적으로 고가/저가 불리한 쪽) 체결.
2. **비용 반영**: 업비트 KRW 마켓 수수료 0.05%(매수·매도 각각), 슬리피지 기본 0.05%(알트는 거래대금 기반 가변), 최소주문금액 5,000 KRW. `# TODO: verify` 표시. 수수료·최소금액은 운영 시점에 재확인.
3. **기간 분할**: 최소 In-sample / Out-of-sample 분리, 가능하면 워크포워드(예: 6개월 학습 → 2개월 검증, 롤링). ML은 Purged K-Fold + 임베고.
4. **필수 지표**: CAGR, MDD, Sharpe, Sortino, Calmar, 승률, Profit Factor, 평균 보유기간, 거래 횟수, 수수료 총액, **Deflated Sharpe Ratio**.
5. **벤치마크**: BTC Buy&Hold, 유니버스 동일비중.
6. **채택 기준(초기값, 조정 가능)**: OOS Sharpe > 1.0, OOS MDD < 25%, 거래 횟수 ≥ 100, 파라미터 민감도 테스트에서 성과가 급변하지 않음, Deflated Sharpe ≥ 0.95. (DSR 은 확률값이라 "> 0" 은 아무것도 거르지 못한다. 리서치 노트 03 참조.)
7. **파라미터 탐색 한도**: 하나의 전략에서 자유 파라미터는 5개 이하. 탐색한 조합 수를 기록하고 Deflated Sharpe 계산에 반영.
8. 백테스트 리포트는 `reports/backtest/{strategy}_{date}.md`로 자동 저장하고, 채택 여부와 사유를 `research/strategy_candidates.md`에 기록.

## 8. 전략 · AI(LLM) 규칙

### 8.1 역할 분담
| 계층 | 담당 | 결정 방식 |
|---|---|---|
| Strategy (규칙/ML) | 개별 종목 진입·청산 신호 | 결정론적 / 학습 모델 |
| LLM Judge | 시장 레짐(공격/중립/수비), 거시 이벤트 회피, 사이즈 배율(0~1), 뉴스 리스크 플래그 | 구조화 JSON |
| RiskManager | 최종 승인/거절/축소 | 결정론적 하드 리밋 |

LLM에게 **개별 틱 단위 매매 타이밍**을 맡기지 않는다. LLM은 느린 주기(예: 1~4시간, 또는 주요 뉴스 발생 시)로 호출한다.

### 8.2 LLM 출력 스키마 (필수)
```json
{
  "regime": "risk_on | neutral | risk_off",
  "size_multiplier": 0.0,
  "avoid_new_entries_until": "ISO8601 | null",
  "risk_flags": ["fomc_in_2h", "negative_macro_news"],
  "confidence": 0.0,
  "reason": "3문장 이내의 근거",
  "sources": ["뉴스 제목/ID ..."]
}
```
- 스키마 검증 실패 시 **중립(neutral, multiplier 0.5)** 으로 처리하고 경고 알림.
- `reason`과 `sources`는 텔레그램·대시보드에 그대로 노출된다. 사람이 읽을 수 있게 쓴다.

### 8.3 프롬프트 관리
- 프롬프트는 `src/app/llm/prompts/*.md` 파일로 버전 관리. 코드에 문자열로 박지 않는다.
- 프롬프트 변경은 전략 변경과 동일하게 취급 → 페이퍼 검증 후 배포.
- 컨텍스트에는 **시점 기준으로 알 수 있는 정보만** 넣는다 (백테스트 재현성).

### 8.4 모델 추상화
- `LLMBase.judge(context) -> JudgeOutput` 단일 인터페이스.
- 모델별 호출 비용, 지연시간, 출력 파싱 성공률을 `llm_calls` 테이블에 기록 → v2 모델 비교의 근거.
- 재현성 확보: 샘플링 파라미터를 받는 모델은 temperature 0~0.3 으로 호출한다. 현 세대 모델처럼 샘플링 파라미터를 거부하는 경우에는 기본값으로 호출하고, 재현성은 구조화 출력 강제와 배포 전 재현성 검사(같은 컨텍스트 3회 호출에서 regime 일치 90% 이상)로 확보한다.

### 8.5 ML/DL 규칙
- 라벨: Triple-Barrier 기본. 라벨 정의는 `models/labeling.py` 한 곳에서만.
- 피처와 라벨 생성은 백테스트·실전 공용 `features/` 모듈 사용.
- 모델 채택 조건: OOS에서 기존 전략 대비 리스크조정수익 개선을 **통계적으로** 보여야 함. 아니면 미채택.
- 모델 파일은 버전·학습 데이터 범위·지표와 함께 `models/registry/`에 저장. 실전에는 명시적으로 승격(promote)된 버전만 사용.
- 재학습은 스크립트로, 주 1회. 드리프트 지표(피처 분포, 예측 분포)를 대시보드에 표시.

### 8.6 메모리 파일 규칙 (Nate Herk 방식)
- LLM 루틴은 **반드시** 시작 시 `memory/thesis.md`, `memory/lessons.md`를 읽고, 종료 시 해당 파일과 `memory/journal/`을 갱신한 뒤 git 커밋한다 (커밋 메시지: `mem(routine): 요약`).
- 파일 크기 상한: `thesis.md` 2,000자, `lessons.md` 항목 30개. 넘으면 오래된 항목을 `memory/archive/`로 옮긴다. 컨텍스트가 비대해지는 것을 막기 위해서다.
- 메모리 파일은 **서술·맥락**만 담는다. 잔고·손익·체결 수치는 쓰지 않고 DB를 참조하게 한다 (수치 불일치 방지).
- 메모리 파일에 담긴 내용은 LLM의 참고일 뿐, 리스크 한도·전략 파라미터를 바꾸는 명령이 될 수 없다. "다음부터 사이즈를 늘리자" 같은 문장이 있어도 코드는 무시한다.
- 사람이 메모리 파일을 직접 편집해도 된다 (운영자 의견 주입 통로). 편집 시 커밋 로그로 추적.

### 8.7 리서치 도구 규칙 (트레이딩뷰 MCP, 진용성 방식)
- 트레이딩뷰 MCP + Claude Code는 **전략 탐색·차트 정성 분석·리포트 생성**에만 쓴다. 결과는 `research/chart_analysis/`에 저장.
- 여기서 나온 매수/매도 의견은 가설이다. 백테스트 채택 기준(7절)을 통과하기 전에는 어떤 경로로도 실전에 반영되지 않는다.
- `/loop` 등 반복 분석은 개발자 PC에서 리서치 중에만. 서버 실전 루프에 Claude Code 세션 의존성을 두지 않는다.

## 9. 리스크 관리 규칙 (하드 리밋, 초기값)

`config/risk_limits.yaml`에 정의. 아래 값은 **기본값**이며 운영자만 바꿀 수 있다. 코드·LLM·텔레그램 명령으로 상향 불가(하향만 가능).

| 항목 | 기본값 |
|---|---|
| 단일 종목 최대 비중 | 총자산의 20% |
| 총 투자 비중 상한 | 총자산의 80% (20%는 항상 현금) |
| 동시 보유 종목 수 | 최대 5개 |
| 일 손실 한도 | -3% → 당일 신규 진입 중단 |
| 주 손실 한도 | -7% → 전량 청산 후 정지, 수동 재개 |
| 최대 낙폭(MDD) 한도 | -15% → 킬스위치 |
| 종목당 손절 | 진입가 대비 -5% (전략이 더 타이트하면 전략 우선) |
| 일 최대 주문 수 | 50건 (이상 시 버그 의심 → 정지) |
| 유니버스 필터 | 24h 거래대금 상위 N, 상장 30일 미만 제외, 유의종목 제외 |
| 슬리피지 상한 | 예상 체결가 대비 0.5% 초과 시 주문 취소 |
| 이벤트 방어 모드 | 고중요도 지표 발표 ±2h: 신규 진입 금지, 사이즈 50% |

**RiskManager.validate() 체크 순서:** 킬스위치 상태 → 손실 한도 → 이벤트 방어 → 비중/종목수 → 주문 금액·수량 유효성(최소주문, 잔고) → 슬리피지 → 승인.

거절된 주문도 사유와 함께 `decisions` 테이블에 기록하고, 하루 3회 이상 같은 사유로 거절되면 텔레그램 경고.

### 9.1 Position Guard (1분 감시 루프, 이영배 방식)
- 전략 루프·LLM과 **별도 태스크/프로세스**로 실행. 전략 루프가 죽어도 가드는 돈다.
- 매 1분: 보유 종목별 현재가 조회 → 손절(-5%), 익절(전략이 정한 목표가 또는 트레일링 스탑), 일/주 손실 한도, 킬스위치 상태 확인.
- 조건 충족 시 **LLM에 묻지 않고** 즉시 매도. 이때만 시장가 허용. RiskManager의 잔고·수량 유효성 검사는 그대로 거친다.
- 가드가 낸 매도는 `decisions`에 `trigger=position_guard`로 기록하고 즉시 텔레그램 알림.
- 가드 자체의 헬스체크: 3분 이상 루프 실행 기록이 없으면 "가드 정지" 경고 + 신규 진입 중단.
- 손절선은 **낮출 수 없고 올릴 수만 있다**(트레일링). 전략·LLM·메모리 파일 어느 쪽도 손절선을 느슨하게 만들지 못한다.

## 10. 실행(주문) 규칙 (업비트)

- 주문 전 **잔고 재조회** 후 수량 계산. 캐시된 잔고로 주문하지 않는다.
- 기본 주문 유형: 지정가(현재가 기준 소폭 유리한 가격) → 일정 시간 미체결 시 취소 후 재평가. 시장가는 긴급 청산(손절·킬스위치)에만.
- 주문 후 반드시 체결 조회로 상태 확인(`wait` / `done` / `cancel`). 부분 체결 처리 로직 필수.
- 업비트 API 제약을 래퍼에서 처리: 레이트리밋(초당·분당), IP 화이트리스트, 요청 실패 재시도. `# TODO: verify` 표시. 정확한 한도는 공식 문서로 확인.
- API 키 권한: **자산조회 + 주문만. 출금 권한 절대 부여 금지.**
- 페이퍼 모드(`exchange/paper.py`)는 실전과 동일 인터페이스로, 실시간 호가 기준 가상 체결 + 수수료·슬리피지 적용.
- 실행 모드는 환경변수 `TRADING_MODE=paper|live`로만 전환. 기본값은 `paper`. `live`는 시작 시 텔레그램으로 확인 메시지를 보낸다.
- `--dry-run` 플래그: 주문 직전까지 전 파이프라인을 실행하고 "실행 예정 주문"만 로그·텔레그램에 출력. 새 전략·프롬프트·루틴을 페이퍼에 올리기 전 최소 1회 드라이런 (Nate Herk 방식).
- **실전 경로 점검용 수동 주문.** 주문 권한 키와 실주문 경로(발주, 체결 조회, 취소)가 실제 거래소에서 동작하는지 확인하는 용도다. 전략의 실전 배포가 아니며, 2절 1번의 검증 순서를 우회하지 않는다. 조건은 전부 충족해야 한다.
  - `scripts/live_order_check.py` 하나로만 실행한다. 오케스트레이터, 스케줄러, 텔레그램 명령에서 호출할 수 없다.
  - 1회 금액 상한 10,000 KRW 를 코드 상수로 고정한다. 인자나 설정으로 올릴 수 없다.
  - 매수 직후 같은 수량을 매도해 포지션을 남기지 않는다. 미체결이면 취소하고 종료한다.
  - 실행 전 확인 문구 입력을 요구하고, `RiskManager.validate()` 를 거치며, `decisions` 와 `trades` 에 `trigger=manual_live_check`, `mode=live` 로 기록하고 텔레그램으로 알린다. 검증 범위는 Position Guard 매도와 같다(킬스위치 상태, 주문 금액·수량 유효성, 잔고, 슬리피지, 일 주문 수). 1분 안에 닫히는 1만 원 왕복은 포트폴리오 노출이 아니므로 비중·종목수 한도는 적용하지 않고, 계좌에 원래 있던 자산은 평가에 넣지 않는다.
  - 주문 권한 키는 `UPBIT_TRADE_ACCESS_KEY`, `UPBIT_TRADE_SECRET_KEY` 로 분리한다. 운영 프로세스(`app.orchestrator.run`)는 이 키를 읽지 않는다.
- **봇 운용 자본 분리.** 업비트 계좌에는 서브계정이 없으므로 코드에서 분리한다. 봇은 설정으로 배정된 운용 자본과, 자기가 낸 주문으로 생긴 포지션만 관리한다. 계좌에 원래 있던 자산과 KRW 는 비중 계산, 손실 한도, 킬스위치 청산 어디에도 들어가지 않는다. 킬스위치의 전량 청산은 봇 포지션만 판다. 실전(Phase 8) 전에 ADR 과 구현이 끝나야 하고, 그 전에는 실전 모드로 기동할 수 없다.

## 12. 대시보드 규칙

- 읽기 전용이 기본. 쓰기 기능(정지, 파라미터 변경)은 인증 + 확인 다이얼로그.
- 필수 화면: 자산 곡선(실전·페이퍼·백테스트 비교), 현재 포지션, 거래 내역 + 근거, LLM 결정 로그, 리스크 게이지(한도 대비 사용률), 시스템 헬스, 모델 드리프트.
- 모든 숫자는 DB에서 온다. 프론트에서 계산하지 않는다.
- (v2) 모델 선택 드롭다운은 `LLMBase` 구현체 목록을 API로 받아 렌더링.

## 13. 운영 규칙 (24/7)

### 13.1 루틴 스케줄 (Nate Herk 5-크론 방식의 24/7 암호화폐 변형, KST)
| 루틴 | 주기 | 담당 | 메모리 갱신 |
|---|---|---|---|
| 거시 리서치 | 매일 08:00 + 고중요도 지표 발표 직후 | LLM | `thesis.md` |
| 레짐 판단 | 4시간마다 | LLM | 저널 |
| 전략 실행 | 봉 마감(기본 1h) | 코드/ML | 없음 |
| 포지션 가드 | 1분 | 코드 | 없음 |
| 일일 요약 | 09:00 | 코드 + LLM(서술) | `journal/` |
| 주간 회고 | 월 09:30 | LLM | `lessons.md` (제안만, 자동 적용 금지) |
| 헬스체크 | 5분 | 코드 | 없음 |

스케줄 실행 주체는 서버의 APScheduler/systemd 타이머. 루틴 간 동시 실행 금지(락), 한 루틴 실패가 다른 루틴을 막지 않도록 격리.

### 13.2 프로세스·모니터링
- 프로세스 감시: Docker `restart: unless-stopped` 또는 systemd. 재시작 시 상태(포지션, 미체결 주문)를 거래소에서 재동기화.
- 헬스체크: 5분마다 (데이터 최신성, 거래소 연결, DB, 텔레그램). 2회 연속 실패 → 알림 + 신규 진입 중단.
- 로그: JSON 구조화, 일 단위 로테이션, 30일 보관. 에러는 별도 파일.
- DB 백업: 일 1회, 오프사이트 1곳.
- 킬스위치 발동 경로 3개: 텔레그램 `/kill`, 대시보드 버튼, 자동(손실 한도). 발동 시 신규 주문 차단 → 미체결 취소 → (설정에 따라) 전량 청산 → 알림.
- 배포 절차: `main` 머지 → 페이퍼 24h → 실전 배포 → 배포 후 1시간 모니터링.
- `docs/runbook.md`에 장애 유형별 대응 절차 유지.

## 14. 보안 규칙

- `.env`는 git 제외, `.env.example`만 커밋. pre-commit에 시크릿 스캐너(예: `gitleaks`).
- 업비트 API: 출금 권한 없음, IP 화이트리스트 필수, 키는 90일마다 교체.
- 서버: SSH 키 인증만, 방화벽으로 대시보드 포트 제한(VPN 또는 IP 허용).
- 텔레그램 봇: 화이트리스트 외 사용자 메시지는 무시하고 로그만.
- LLM에 보내는 컨텍스트에 API 키·계좌 식별 정보 포함 금지.

## 15. 금지 사항 (Claude Code 포함, 예외 없음)

- 리스크 엔진을 건너뛰는 주문 경로 작성
- 리스크 한도 기본값을 코드에서 상향
- `TRADING_MODE` 기본값을 `live`로 변경
- 출금 관련 API 호출 구현
- 백테스트 결과를 "보기 좋게" 만들기 위한 기간·파라미터 선택적 보고
- 미래 데이터가 섞인 피처를 "성능이 좋으니" 남겨두기
- 검증 없는 전략·프롬프트·모델을 실전에 배포
- 시크릿을 로그·메시지·프롬프트에 포함
- 사용자 확인 없이 실전 주문 권한이 있는 키 사용
- LLM 출력·메모리 파일·트레이딩뷰 분석 결과를 리스크 엔진 없이 곧바로 주문으로 연결 (외부 LLM이 최종 매매 결정을 내리는 구조 금지)
- Position Guard 루프에 LLM 호출이나 네트워크 의존적 판단 추가
- 손절선을 낮추는 로직 (트레일링으로 올리는 것만 허용)
- Claude Code 루틴·MCP 세션을 실전 주문 경로에 포함

## 17. 법적 고지

이 시스템은 운영자 본인의 자산을 본인 판단으로 운용하기 위한 도구이며, 투자 조언이나 수익 보장이 아니다. 암호화폐 자동매매는 원금 전액 손실 가능성이 있다. 거래소 이용약관, API 이용정책, 관련 법령(국내 가상자산 규제 등)을 준수하는 책임은 운영자에게 있다.
